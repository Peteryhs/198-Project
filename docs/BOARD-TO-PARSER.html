Firmware contract — Tally repetition model

Your job is to sample the accelerometer and ship the numbers. The Linux side of the shield cuts the set into repetitions, computes the 31 features, runs the model and returns one verdict. You never compute features.

Where the code goes

Everything below lives in hardware/198project/. Two files are empty today and are where the sender belongs; the sketch only gains three call sites.

Block 1 — data_transfer.h

Block 2 — data_transfer.cpp

#include "data_transfer.h"
#include <Arduino.h>

static unsigned long seq = 0;

void tally_begin(void) {
    seq = 0;
    Serial1.print("#TALLY1 fs=100 unit=g ax=+x ay=+y az=+z\n");
}

void tally_sample(float ax, float ay, float az) {
    char line[56];
    int n = snprintf(line, sizeof line, "S %lu %+.8f %+.8f %+.8f\n",
                     seq++, ax, ay, az);
    if (n > 0) Serial1.write((const uint8_t *)line, (size_t)n);
}

void tally_end_set(const char *reason) {
    Serial1.print("E "); Serial1.print(reason); Serial1.print('\n');
}

%+.8f forces the sign and exactly eight decimals, so every line matches the contract. This needs the R4's snprintf, which supports %f; on an AVR board you would have to link the float printf library.

Call site 1 — setup(): the sketch currently opens Serial at 9600. The stream needs its own port at 115200.

void setup() {
    Serial.begin(9600);        // keep: your debug console
    Serial1.begin(115200);     // the shield's Linux side reads this one
    tally_begin();
}

Call site 2 — loop(): replace the delay(200) printing loop with a 10 ms scheduler. One sample every 10,000 µs, no blocking delay.

static unsigned long next_us = 0;

void loop() {
    unsigned long now = micros();
    if ((long)(now - next_us) < 0) return;
    next_us += 10000;                       // 100 Hz

    float x = accelerometer1.convertX();     // sensor 1 is the streamed limb
    float y = accelerometer1.convertY();
    float z = accelerometer1.convertZ();
    tally_sample(x, y, z);

    // see call site 3
}

Call site 3 — ending the set: a set ends when the student stops. Pick one trigger and send exactly one E line per set.

    if (digitalRead(BUTTON_PIN) == LOW) {     // button press ends the set
        tally_end_set("done");
        next_us = micros() + 10000;
    }

If you have no button yet, use a fixed count instead: if (seq == 3000) tally_end_set("done"); ends the set after 30 s. The next set must restart at seq 0, so call tally_begin() again or reset the counter.

Serial link

115200 baud, 8 data bits, no parity, 1 stop bit. One ASCII message per line, ending in \n; \r\n is accepted. A line including its terminator must be at most 64 bytes. Send nothing else: no prompts, no debug text, no blank lines, no byte-order mark.

The three messages

messagewhennotes
#TALLY1 fs=100 unit=g ax=+x ay=+y az=+zonce after resetsession header, exact field order. Not a comment: it is required.
S <seq> <ax> <ay> <az>every sampleone line per sample, 100 Hz
E doneset finishedalso E aborted, E overflow to end a discarded set

Sample fields

fieldrule
seqbase-10 integer 0…2147483647, starts at 0 for every set, increments by exactly 1, never repeats. A gap invalidates the set.
ax, ay, azsigned decimal in g, exactly 8 digits after the point, leading + or -. No exponent, no NaN, no infinity. Example: -0.08087663

No timestamps: the rate is fixed at 100 Hz and seq carries ordering. Eight decimals reproduce the recorded data — at that precision the Linux side matches the training features on every slot, so nothing is lost in transmission.

{"status":"ok_unverified_rate","end":"done","sample_count":7556,"vector_count":38,

That is a real reply, captured from a replayed recording. On a live serial port the status reads ok and measured_rate_hz carries the arrival rate the parser measured; replay has no timing evidence, which is why this one says ok_unverified_rate and null.

verdict is correct or wrong, taken from mean_p_wrong >= 0.5 across the repetitions. vector_count is how many repetitions were scored. One JSON line per set.

Timing and throughput

Sample at 100 Hz. A 46-byte line at 100 Hz is about 4,600 bytes/s against a nominal 11,520 bytes/s at 115200 8N1, so the link has headroom; at the 64-byte cap the rate would be 6,400 bytes/s, still inside. 9600 baud would not fit. The parser measures the real arrival rate and flags anything outside 95–105 Hz.

The model was fitted on 100 Hz data and the parser does not resample. If your loop drifts, fix the loop; do not re-timestamp the samples.

Axes and mounting

x, y, z are the accelerometer axes as recorded in training, in g, gravity included — do not remove the 1 g offset, and do not rotate or reorder axes. The features assume the same sensor orientation on the limb as the recordings.

Failure rules

  • A gap, duplicate, malformed, over-long or unexpected line invalidates the whole set. Send E aborted and start again at seq 0.
  • Never score a partial set. If your buffer fills, send E overflow; the parser discards everything up to the marker.
  • A set with fewer than 3 detected repetitions returns a status saying so, with no verdict. That is a real answer: the student moved too little.
  • Cap is 60,000 samples per set (600 s at 100 Hz). Beyond that the parser returns aborted.
  • If the link stalls mid-line, drop the line and resend the sample with the appended sequence numbers — never half a line.

Bench checklist

  1. Send the header, 200 samples and E done: expect a reply with measured_rate_hz near 100.
  2. Confirm gap_count is 0 across a full set under load.
  3. Run one real set end to end and check vector_count matches the repetitions you counted by hand.
  4. Unplug mid-set and confirm the next set starts clean at seq 0 after a reset.
