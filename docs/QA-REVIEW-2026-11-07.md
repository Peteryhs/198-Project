# QA review — Codex modelling branch, 2026-11-07

Independent check of `codex/embedded-modelling` (5 commits, `c8a09e1..27bbca0`) by a reviewer who
did not write it. Method: rerun everything from a clean environment on a different machine, then
compare. Nothing below is taken from the agent's own report.

## Verdict

The work is sound and the numbers are real. Two claims I could not reproduce as stated, and both turn
out to be environment sensitivity rather than error. Three genuine gaps remain, listed at the end.

## What reproduced

| Check | Agent reported | I measured | Verdict |
| --- | --- | --- | --- |
| Quality, weighted linear, unclipped, LOSO-30 | 86.9883% | 0.869883 | reproduced exactly |
| Learning curve, 10 / 20 / 29 training volunteers | 85.4532 / 86.8421 / 86.9883% | 0.855263 / 0.868421 / 0.869883 | reproduced to 4 dp |
| Pipeline unit assertions | pass | pass (`scripts/test_realtime_pipeline.py`) | reproduced |
| Raw dataset fetch | 1,484 files, CRC-checked | present at `data/phytmo/inertial/upper` | reproduced |

The training-data lineage is intact: the weighted linear arm lands on the same 0.8699 I got from the
committed feature bags, and the exercise head's 94.6% is plausible for three well-separated
exercises.

## Where my rerun disagreed, and why it is not a defect

`scripts/verify_linear_export.py` asserts that the C export matches a fresh Python refit.

- On my default environment (scikit-learn 1.9.1, numpy 2.5.4, scipy 1.18.1) it **fails**:
  largest coefficient difference 0.399 in `exercise_coef`.
- With the pinned versions from `scripts/requirements-modelling.txt`
  (scikit-learn 1.7.2, numpy 2.3.4, scipy 1.16.3) it **passes with every difference exactly 0.0**.

So the export is faithful; the refit is not portable across library versions. Accuracy was
identical in both runs, so this is coefficient drift inside the solver, not a wrong model. It is
still a reproducibility hole worth closing (see gap 3).

## Honesty checks that held up

- The error head is **not** faked. `rt_error_category()` returns the literal string
  `"not enough evidence to say"`, and the report calls error-type accuracy "not measurable — no
  labels" instead of reusing the quality score.
- The export rejects non-finite inputs and returns 0 rather than a garbage prediction.
- "Not measured" is stated where it applies: no board attached, `expf` unresolved, sections are
  unlinked object sizes excluding core, libm and runtime; the 0.208 ms figure is labelled an
  estimate.
- Repetition counts are called detector output, not repetition ground truth.

## Measurements I confirmed independently

- Exported coefficients: 512 B of float32 across both heads; header 2,984 B; NPZ 1,617 B.
- Cortex-M4 object (`clang --target=arm-none-eabi`, `-Oz`): 1,013 B total, of which 324 B code,
  372 B exercise coefficients, 124 B quality coefficients, 12 B intercepts.
- Clipping is software clipping of ±16 g recordings, not a physical ADXL335. The −0.29 point change
  is therefore not evidence that the real sensor is safe. The bench test is still owed.

## Gaps that must be closed before more training rounds

1. **The pair is never modelled.** The device's whole idea is two sensors on one limb measuring the
   angle between segments. Every model on this branch consumes a *single* segment's 31 features
   (`--sensor Larm`), and the all-placement arm treats each recording independently. Nothing here
   fuses upper and forearm, so nothing here exercises the actual sensing concept. This is the
   largest gap and it predates the branch.
2. **The export is not real-time.** `realtime_model.h` takes 31 already-computed features, and the
   segmentation is offline and non-causal: it needs the repetition to finish. The on-device feature
   buffer and the causal detector are both absent. "Real-time" is currently a plan, not a thing
   that runs.
3. **Reproducibility is not enforced.** Nothing pins the environment for the reader; a fresh
   `uv run` picks newer libraries and breaks the export assertion. Add a lockfile or a bootstrap
   script, and fail loudly on a version mismatch.

## What I would tell the next agent

Do not re-derive the baseline; it is solid and reproducible. Spend the next round on the pair
fusion (gap 1) and on making the pipeline honest about the causal constraint (gap 2), then on the
simulation the team asked for — and validate any simulator against these recordings before trusting
a number that comes out of it.
